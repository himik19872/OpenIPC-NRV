# Архитектура

Описание устройства системы и принятых технических решений.

---

## Компоненты

| Сервис | Технология | Порт | Назначение |
|---|---|---|---|
| `backend` | Go 1.22, chi, pgx | 8080 | REST API, бизнес-логика |
| `webui` | React 18, TypeScript, nginx | 3001 | Веб-интерфейс |
| `mediamtx` | MediaMTX | 8554, 8888, 8889, 9997 | Приём RTSP, раздача HLS/WebRTC |
| `rtsp-proxy` | nginx (модуль `stream`) | 9784 | RTSP для внешних систем |
| `postgres` | PostgreSQL 16 | 5434 | Метаданные |
| `minio` | MinIO (S3) | 9000, 9001 | Видеоархив |
| `nats` | NATS JetStream | 4222 | Шина событий |
| `ai-detector` | Python, YOLOv8 | — | Детекция объектов |

Бэкенд работает в режиме `network_mode: host`, остальные — в bridge-сети.
Это нужно, чтобы бэкенд напрямую видел камеры в локальной сети и мог
обращаться к сервисам по `localhost`.

## Слои бэкенда

```
cmd/server/main.go          точка входа, сборка зависимостей
        │
internal/api/
  router.go                 маршруты, middleware (JWT, CORS, логи)
  handlers/                 HTTP-обработчики: разбор запроса, ответ
        │
internal/service/           бизнес-логика
  camera_service.go         камеры, регистрация потоков, SSH, PTZ
  camera_status_monitor.go  опрос медиасервера, статусы, очистка путей
  camera_scanner.go         поиск камер в подсети
  ptz_service.go            ONVIF-клиент
  camera_ssh.go             команды на камерах
  event_service.go          события детекции
  acs_service.go, acs/      адаптеры СКУД
        │
internal/repository/
  postgres/                 доступ к БД, миграции
  minio/                    S3-хранилище архива
        │
internal/nats/              подписка на события от детектора
internal/tunnel/            WireGuard (заготовка)
```

Обработчики не обращаются к базе напрямую — слой сервисов владеет логикой,
репозитории отвечают только за хранение.

## Жизненный цикл потока камеры

```
1. Добавление камеры
   POST /cameras → CameraService.Create
        │
        ├─▶ запись в PostgreSQL (камеры, креды в settings)
        └─▶ регистрация пути в MediaMTX:
            POST /v3/config/paths/add/{uuid}
            {source: "rtsp://user:pass@IP/stream=0", rtspTransport: "tcp"}
            + отдельный путь {uuid}_sub для субпотока

2. Приём потока
   MediaMTX подключается к камере по RTSP (TCP),
   перекодирует в HLS (fmp4) и WebRTC

3. Просмотр в браузере
   GET /cameras/{id}/hls/index.m3u8?token=<jwt>
        │
        ├─ проверка JWT вручную (обработчик вне JWT-группы)
        ├─ запрос к MediaMTX с cookiejar (сессия HLS)
        └─ переписывание плейлиста: добавление ?token= к сегментам
           и к EXT-X-MAP (init-сегмент fmp4)

4. Мониторинг
   CameraStatusMonitor раз в 15 секунд:
        ├─ GET :9997/v3/paths/list → определение ready
        ├─ обновление status в БД (online/offline)
        └─ удаление путей, для которых нет камеры в БД
           (внешние адреса cameras/* исключены — их создаёт
            ExternalRTSPService, а не камера)

5. Внешний доступ
   ExternalRTSPService при старте и при смене номера канала:
        POST /v3/config/paths/add/cameras%2F{N}%2Fstreaming%2Fmain
        {source: "rtsp://127.0.0.1:8554/{uuid}"}

   Источник — внутренний путь MediaMTX, а не камера.
   Так внешние потребители получают копию уже принятого потока,
   и подключение к камере остаётся одно.
```

### Почему признак субпотока в пути, а не в query

Изначально субпоток запрашивался как `/hls/index.m3u8?stream=sub`.
Это не работало: hls.js разрешает относительные ссылки из плейлиста
самостоятельно и **не переносит query-параметры** в запросы сегментов.
В результате сегменты субпотока уходили на основной поток, и медиасервер
отвечал ошибкой авторизации.

Решение — кодировать поток в пути: `/hls/sub/index.m3u8`. Путь наследуется
корректно, так как плейлист и сегменты лежат в одном каталоге.

## Схема базы данных

```
sites ─────────┐
               │
cameras ◀──────┘   id, name, ip, mac, firmware,
   │               main_stream, sub_stream, wg_ip,
   │               status, settings (JSONB), hw_info,
   │               channel_number (номер для внешнего RTSP)
   │
   ├──▶ detection_events    camera_id, timestamp, object_class,
   │                        confidence, bbox, track_id
   │
   ├──▶ recordings          start_time, end_time, file_path,
   │                        file_size, resolution, codec
   │
   └──▶ acs_events          door_id, event_type, card_number

acs_controllers            name, vendor, ip, port, credentials
users                      username, password_hash, role
push_tokens                user_id, token, platform
wireguard_peers            site_id, pubkey, ip, last_seen
```

Настройки, которые могут расширяться (`settings`, `hw_info`, `metadata`,
`config`), хранятся в `JSONB` — это позволяет добавлять поля без миграций.
Например, признак поддержки PTZ лежит в `settings.ptz`.

### Миграции

Применяются автоматически при старте бэкенда через `golang-migrate`.
Файлы: `{версия}_{название}.up.sql` и `.down.sql`.

Особый случай: база, созданная до внедрения миграций, не имеет таблицы
`schema_migrations`. Функция `adoptExistingSchema` определяет текущую
версию по набору колонок и вызывает `Force`, иначе `Up()` упал бы на
попытке создать существующие таблицы.

## Ключевые технические решения

### MediaMTX как медиасервер

Отвечает за приём RTSP, раздачу HLS и WebRTC, запись. Пути регистрируются
через HTTP API бэкендом. Пути хранятся **в памяти** и теряются при
перезапуске MediaMTX — поэтому `RestoreStreams` перерегистрирует их при
старте бэкенда.

### Транспорт TCP для RTSP

Потоки 4K (3840×2160) по UDP теряют RTP-пакеты, из-за чего HLS-муксер
падает с ошибкой `unable to extract DTS: too many reordered frames`.
Принудительный TCP устранил проблему.

### HLS-вариант fmp4

`hlsVariant: mpegts` при коротком сегменте (1 с) вызывал постоянное
пересоздание муксера и падения на B-кадрах. Переход на `fmp4` с сегментом
2 с сделал воспроизведение стабильным.

### Presigned-ссылки для архива

Видеофайлы не проходят через бэкенд: клиент получает временную ссылку на
MinIO. Для этого используются **два клиента** — внутренний (обмен данными)
и внешний (подпись ссылок). Подпись зависит от хоста, поэтому подписать
ссылку внутренним адресом нельзя: браузер получил бы нерабочий URL.

### Авторизация HLS и снапшотов
Браузерные теги `<video>` и `<img>` не могут отправлять заголовок
`Authorization`. Поэтому:

- HLS: токен в query (`?token=`), проверяется в обработчике;
- снапшот: токен в query (`?jwt=`), обработчик вынесен из JWT-группы.

Плейлист переписывается на лету — токен добавляется к каждому сегменту и
к `EXT-X-MAP` (init-сегмент fmp4, без него воспроизведение не начнётся).

### Управление камерами по SSH

Команды выполняются через системный `ssh` с `sshpass` (пароль передаётся
через переменную окружения, а не в аргументах, чтобы не попадать в список
процессов). Выбран системный клиент вместо Go-библиотеки: камеры OpenIPC
используют busybox и dropbear со специфичным набором алгоритмов.

Сейчас это **резервный** путь: основные настройки идут через HTTP API
прошивки (Majestic), а SSH остаётся для камер без API.

### Настройки камеры через HTTP API прошивки

Majestic принимает частичный патч конфигурации: в теле запроса уходят
только изменяемые разделы, остальные настройки камеры не затрагиваются.

Ключевое решение — **поля структуры настроек объявлены указателями**.
При обычных типах ноль и `false` были бы неотличимы от «не менять»:
правка одной строки OSD отправляла бы на камеру нули во всех остальных
полях, и камера отвечала `400 Bad Request`, а ночной режим и кодирование
сбрасывались бы. Указатель же явно различает «не трогали» и «установили
в ноль».

Сборки Majestic различаются набором эндпоинтов: у одних есть
`/api/v1/sources` и `dashboard.cgi`, у других только `/api/v1/config.json`
и `status.cgi`. Поэтому возможность управления определяется по чтению
конфигурации, а страницы состояния и перезапуска перебираются по списку.

### Внешний RTSP-доступ

Задача — отдавать потоки сторонним системам, не наращивая число
подключений к камерам. Камеры ограничивают число одновременных
RTSP-сессий и при исчерпании лимита отвечают `453 Live memory budget
is full`, после чего поток пропадает у всех, включая архив.

Решение — публиковать в MediaMTX пути, источником которых служит
**внутренний путь, а не камера**:

```
POST /v3/config/paths/add/cameras%2F0%2Fstreaming%2Fmain
{"source": "rtsp://127.0.0.1:8554/{uuid}"}
```

Три следствия этого решения:

1. **Нагрузка на камеру не растёт** — MediaMTX раздаёт уже полученный
   поток, дополнительных сессий к камере не появляется.
2. **OSD одинаков для всех.** Надпись встраивается камерой аппаратно
   (`video0.osd`, `video1.osd`) и приходит уже в кадре. NVR её не
   накладывает и не может изменить отдельно для внешних потребителей.
3. **Перекодирования нет** — качество и задержка такие же, как при
   прямом подключении к камере.

Отдельный порт `9784` обслуживает nginx (модуль `stream`): MediaMTX 1.20.1
поддерживает только один RTSP-порт, а авторизация в нём задаётся глобально.
Требовать пароль на основном порту нельзя — его не передают внутренние
потребители, поэтому внешний доступ вынесен на отдельный порт.

Имя пути содержит слеши, и при вызове API их обязательно кодировать
(`cameras%2F0%2Fstreaming%2Fmain`) — иначе MediaMTX создаст путь с другим
именем.

### Снапшоты с резервным путём

Кадр запрашивается напрямую у камеры — путь зависит от производителя.
Если ни один путь не сработал, кадр извлекается из HLS-потока через
`ffmpeg`. Это нужно для камер OpenIPC: при двух активных H.264-потоках
аппаратные скейлеры SoC заняты, и `/image.jpg` возвращает 503.

## Поток данных AI-детекции

```
Камера ──RTSP──▶ MediaMTX ──RTSP──▶ frame_publisher (ffmpeg)
                                          │ 1 кадр/с, 640px, JPEG
                                          ▼
                                    NATS: cameras.{id}.frame
                                          │
                                          ▼
                                     ai-detector (YOLOv8 + ByteTrack)
                                          │ объекты, треки
                                          ▼
                                    NATS: cameras.{id}.detection
                                          │
                                          ▼
                              DetectionSubscriber (бэкенд)
                                          │
                                          ▼
                                  PostgreSQL: detection_events
```

Формат сообщения с кадром: первые 36 байт — UUID камеры, остальное — JPEG.
